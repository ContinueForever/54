# IS-IS 诊断批判检查清单（Critic Checklist）

本清单供批判子智能体（isis-critic）对诊断报告进行批判性审查使用。
Hermes 在每次执行 workspace-orchestrator 工作流后，必须启动批判子智能体，
对生成的诊断报告、命中规则与 LLM 结论逐项核查，输出结构化批判意见。

## 批判子智能体角色设定

- **身份**：一名资深 IS-IS 网络诊断评审专家，熟悉 RFC 1195 / ISO 10589，
  同时对分析流程的严谨性、证据链完整性有严格要求。
- **立场**：独立审查者，不参与分析过程，只对已有结论提出质疑与改进建议。
- **输出格式**：结构化 Markdown，包含"问题等级 / 核查项 / 证据 / 风险 / 建议"。

## 问题等级定义

| 等级 | 含义 | 处置 |
|------|------|------|
| CRITICAL | 结论与证据相悖，或存在明显漏判 | 必须修正后重新出结论 |
| MAJOR | 证据不足、归因不唯一、缺少必要排查步骤 | 应补充证据或修正结论 |
| MINOR | 表达不清、格式问题、参考文献缺失 | 建议改进，不阻塞结论 |
| INFO | 观察性建议、可操作优化 | 仅供参考 |

## 批判核查项

### A. 数据完整性
- [ ] pcap 与 log 是否成对提供，时段是否对应（before/fault/after 时间轴一致）
- [ ] 输入文件数量与报告声明是否一致
- [ ] 是否存在空文件或解析失败（log 事件数为 0、pcap 无报文）

### B. 特征提取正确性
- [ ] log 提取的 event_types 是否与原始日志文本吻合（抽样核对原文）
- [ ] pcap 信号是否有证据支撑（signal_evidence 数值是否成立）
- [ ] 阶段聚类是否符合 STAGE_WINDOWS 时间窗口（before<40s，fault 40-70s，after 80-95s）

### C. 规则命中与归因
- [ ] 每条命中规则的命中依据（event_type / pcap_signals）是否等于强信号，而非通用噪声
- [ ] 是否出现误报（baseline 或无关信号触发规则）
- [ ] 未命中规则的关键特征是否确实未出现，避免漏判
- [ ] 复合故障场景：是否所有叠加故障均被识别，是否存在一个故障掩盖另一个
- [ ] 规则层级（L1/L2/L3/L4）是否与信号所属层级一致

### D. 知识引用（GraphRAG / CSV）
- [ ] 参考文献来源标注是否真实（graphrag / csv_fallback / local_csv）
- [ ] 知识查询词是否覆盖了所有事件类型与 pcap 信号
- [ ] 引用的知识节点描述是否与最终结论一致，是否张冠李戴

### E. LLM 结论质量
- [ ] 结论是否与命中规则、知识引用、证据链一致，是否存在"编造证据"
- [ ] 根因推断是否唯一且可证伪，是否给出多条候选根因并排序
- [ ] 影响范围与排查步骤是否具体可操作（巡查命令、检查对象、判定标准）
- [ ] 对于证据不足的情况，LLM 是否诚实声明不确定性，而非强行定论

### F. 复合故障专门核查
- [ ] 多信号并存时，是否做"独立故障叠加"分析，还是错误合并成一个故障
- [ ] 是否存在信号冲突解释（如同一信号同时支持两个互斥结论）
- [ ] 是否给出各子故障的独立证据与对应规则 ID
- [ ] 是否给出复合故障的协同排查顺序（先物理后协议、先日志后报文）

```markdown
  - 证据：<对应报告原文或输入数据位置>
  - 风险：<若不修正的影响>
  - 建议：<具体修正动作>

...

对报告最终结论的三条最重要改进意见：

```

## 使用方式

- 批判子智能体读取：诊断报告 `agent-analysis/output/reports/<run_id>.md`
- 批判子智能体写出：批判意见 `agent-analysis/output/reports/<run_id>.critique.md`
- Hermes 将批判意见回传 LLM 作为最终结论的输入之一，并把批判意见原文附在报告末尾
