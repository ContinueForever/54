2. 核心对比案例

以下案例全部使用同一份输入数据（同 pcap、同 log）的整改前旧报告与整改后新报告的真实输出做对比。

案例 1：link-down 场景 — 从"只看日志声明"到"pcap 数值证据"

同一输入：link-down.pcap（60 包）+ link_down.log（2 行日志）。

整改前（run_20260811_163347）
输入数据
- pcap: 1
- log: 1

## 命中规则
- [L2] L2-R001 adjacency_down: ...

## GraphRAG 知识图谱结果
- [graphrag_answer] adjacency down:          ← 空描述
- [graphrag_answer] link down:               ← 空描述

## LLM 特征摘要
- pcap link-down.pcap: pdus=60, types=[L2_IIH]
                                            ← 无阶段差异、无源ID
整改后（run_20260819_190655）
## pcap 协议信号
- link-down.pcap:
  - NEIGHBOR_LOSS_AT_FAULT
    （R02 IIH: before=10, fault=0）   ← 数值证据

## 命中规则
- [L2] L2-R001 adjacency_down: ...        ← 两路印证

## GraphRAG 知识图谱结果
- [来源:graphrag] 开放问题组合查询:
  若干+h系统分析（Entity 62/15 引用）  ← 有实质知识

## LLM 特征摘要
- pcap: signals=[NEIGHBOR_LOSS_AT_FAULT]  ← 信号进LLM

改进点：

  • 报告新增"pcap 协议信号"节：明确"R02 的 Hello 包在故障窗口从 10 个降为 0 个"，把故障证据从文本声明落到了报文数量
  • 规则命中同时被 log 事件（adjacency_down）与 pcap 信号（NEIGHBOR_LOSS_AT_FAULT）两路证实，误报概率下降
  • 知识查询从两个空的"图节点命中"变成一个有实质内容的图谱回答

案例 2：hello-timer-mismatch — pcap 给出"字段级"证据

同一输入：hello-timer-mismatch.pcap（90 包，R02 间隔 3s→1s、Holding 9→10）。

整改前
## 命中规则
- [L2] L2-R004 hello_timer_mismatch

依据来源：log 一行文本
"Holding timer mismatch"
                            ← 只有文本声明，
                              无具体数值，
                              无法定位到设备
整改后
## pcap 协议信号
- hello-timer-mismatch.pcap:
  - HELLO_INTERVAL_CHANGE
    （R02 Hello 间隔: 3.0s -> 1.0s）
  - HOLDING_TIMER_CHANGE
    （R02 Holding: [9] -> [10]）

## per_source 明细（特征字典）
"000000000002": {
  "stages": {
    "before": {"holding_values": [9],
                "hello_intervals_s": [3.0]},
    "fault":  {"holding_values": [10],
                "hello_intervals_s": [1.0]}}
}

改进点：故障证据细化到字段级（Hello 周期 3.0s→1.0s、Holding 9→10）和设备级（可定位到 R02）。日志只给出"定时器不匹配"的结论，pcap 给出能复核的参数变更过程。

案例 3：duplicate-system-id — pcap 独立检出"双 MAC 冲突"

整改前
## 命中规则
- [L3] L3-R002 duplicate_system_id

## 特征字典
"duplicate_system_id": true     ← 1 个布尔值，
                                  无冲突细节，
                                  无法区分哪台设备
整改后
## pcap 协议信号
- duplicate-system-id.pcap:
  - DUPLICATE_NEIGHBOR_SYSTEM_ID
    （SystemID 000000000002 关联多个源MAC）
  - SOURCE_ID_MAC_CONFLICT

## LLM 特征摘要
- pcap: signals=[DUPLICATE_NEIGHBOR_SYSTEM_ID,
        HELLO_INTERVAL_CHANGE, ...]

改进点：从单一布尔值扩展为"具体 System ID + 多个源 MAC"的可操作证据，且该证据来自 pcap 独立分析，即使日志未提示也能检出。

案例 6：规则精度 — 消除两处误命中

整改初版曾把过泛信号接入规则，实测触发跨场景误报；已通过"信号选择"修正：

场景初版误报修正后
hello-timer-mismatch误命中 L3-R003 area_mismatch（因 PARAMETER_VALIDATION_ALERTS 属通用信号）area 规则不再绑定通用信号，L3-R003 仅由 log 事件驱动
netem-loss-delay误命中 L2-R004 hello_timer_mismatch（抖动 3.0→2.8s 触发 HELLO_INTERVAL_CHANGE）定时器规则改用确定性信号 HOLDING_TIMER_CHANGE，仅命中 L4-R001
duplicate-system-id误命中 L2-R004（干扰场景 Hello 间隔为 0.5s）仅命中 L3-R002（正确）
结论：规则信号选择上，优先使用"该故障独有的确定性信号"（如 HOLDING_TIMER_CHANGE、DUPLICATE_NEIGHBOR_SYSTEM_ID、LINK_PROBE_DEGRADATION），避免使用多场景共有的通用报警信号（PARAMETER_VALIDATION_ALERTS）和对时序抖动敏感的测量信号（HELLO_INTERVAL_CHANGE）。

3. 阶段 A：让 pcap 纳入规则判定（解决 P1~P4）

A1. 特征字典补充字段（pcap_feature.py）

复用 isis_simulator.verify 的 aggregate() 补齐此前缺失的关键记账，输出新增三个字段：

  • pcap_signals：协议异常信号集合（来自 detect_anomalies，13 类检测全量接入）
  • signal_evidence：每条信号的可读数值证据
  • per_source：按源 System ID 输出每阶段计数 / Holding / 区域 / 认证 / PDU 长度 / Hello 间隔

A2. 异常检测接入

extract_features() 直接调用 detect_anomalies(packets)，13 类信号从仿真器自检工具升级为诊断流水线的一等公民。唯一代码改动在 agent-analysis 侧，仿真器逻辑未改，行为一致。

A3. 新增 pcap 驱动规则（config/diagnosis_rules/*.json）

规则新增 pcap_indicators 声明，实现 pcap 信号到规则的双路命中：

规则pcap_indicators信号来源场景
L2-R001 adjacency_downNEIGHBOR_LOSS_AT_FAULTlink-down / lsp-suppression / auth-mismatch
L2-R002 auth_failureINITIALIZING_NEIGHBOR_PRESENTauth-mismatch
L2-R003 circuit_type_mismatchCIRCUIT_TYPE_CHANGE, MIXED_HELLO_PDU_TYPEScircuit-type-mismatch
L2-R004 hello_timer_mismatchHOLDING_TIMER_CHANGE（确定性信号）hello-timer-mismatch
L2-R005 mtu_mismatchINTERFACE_MTU_CHANGEmtu-mismatch
L3-R002 duplicate_system_idDUPLICATE_NEIGHBOR_SYSTEM_ID, SOURCE_ID_MAC_CONFLICTduplicate-system-id
L4-R001 ping_unreachableLINK_PROBE_DEGRADATIONnetem-loss-delay
实现说明：初始映射曾把 PARAMETER_VALIDATION_ALERTS 关联到 L3-R003、把 HELLO_INTERVAL_CHANGE 关联到 L2-R004，实测发现误报（详见案例 6），已修正为上述最终映射。

A4. 规则引擎支持 pcap 信号（engine.py _match_rule）

在原有 log 事件匹配之外新增 pcap 信号匹配分支，两路命中彼此独立、可并列出现，互不覆盖。

A5. 报告增加"pcap 协议信号"节

报告新增节，逐条列出信号及数值证据，与命中规则并列展示（见案例 1 的新版报告节选）。

4. 阶段 B：让 GraphRAG 知识进入 LLM 诊断（解决 P5~P7）

B1. LLM prompt 注入知识结果

新增"知识图谱参考"节，把知识查询结果（含来源标签）注入提示词，要求 LLM 依据知识图谱推理：

## 知识图谱参考
- [来源:graphrag] adjacency down, link down 与 pcap 协议信号
  NEIGHBOR LOSS AT FAULT 同时出现的 IS-IS 故障原因、影响与排查步骤:
  ### IS-IS 故障概览：Adjacency Down 与 Link Down 关联分析
  ... [Data: Entities (62, 15); Relationships (130, 44)]

B2. 查询词改造

事件名原文（字面检索）→ 组合开放问题（实体映射 + 跨节点检索）。为控制耗时（单次 GraphRAG 查询约 30~90 秒），事件与信号合并为单次查询；同时修复了中文 body 的 latin-1 编码错误（body.encode("utf-8")）。

B3. pcap 信号并入查询来源

pcap 信号（如 NEIGHBOR_LOSS_AT_FAULT）与 log 事件一同进入知识查询，协议层信号同样获得知识支撑。

B4. 报告标注知识来源

报告每条知识条目前缀标注来源三态：[来源:graphrag] / [来源:csv_fallback] / [来源:local_csv]。服务端对空回答改为降级 CSV（详见 C1），空 graphrag 命中不再出现。

8. 已知限制与后续建议

  • 外部模型响应较慢：Qwen/Qwen3.5-27B 单次知识查询 45~75s，偶发超时（引擎超时已放宽至 180s）；超时后自动降级 CSV，不影响报告生成
  • agent-analysis 诊断 LLM 仍指向 kimi-k3（配额已耗尽）：当前 LLM 结论为降级结构化提示 + 规则 + 知识参考；如需切换为硅基流动 / 内网 vLLM，改动 agent-analysis/.env.project 即可
  • 知识索引规模偏小：24 节点 / 53 边，建议继续扩充 RFC 深度知识与甲方专家规则（knowledge-builder）
  • 索引由旧模型构建：索引实体抽取由 kimi-k3 完成，若发现实体质量下降，需重建索引（重建后服务自动重启逻辑已就位）
