pcap 与 log 的诊断参与方式、现存问题与优化方案

面向开发与运维人员的说明文档：两种数据源是什么、当前如何参与诊断、存在哪些问题、如何优化

适用项目：54所卫星网络 IS-IS 智能分析平台（agent-analysis / isis-simulator / graphrag）

目录： 1. 整体流程 2. 数据源说明 3. pcap 字段级解析与特征提取 4. 案例分析 5. 当前项目存在的问题 6. 优化方案（三个阶段） 7. 优化后的数据流与验收标准

1. 整体流程

本平台的故障诊断流水线（agent-analysis）按固定顺序执行以下步骤：

  1. 加载数据：读取输入目录下的 pcap 文件（网络报文）与 log 文件（设备日志）
  2. 特征提取：对 pcap 做协议解析与统计，对 log 做正则事件匹配
  3. 知识查询：将识别出的事件类型作为查询词，向 GraphRAG 服务（:9200）查询知识
  4. 分层检查：L1 物理 / L2 链路 / L3 路由 / L4 应用四层规则逐层匹配
  5. LLM 诊断：将特征摘要与命中规则交给语言模型生成结论
  6. 报告生成：输出 Markdown 报告、JSON 追踪记录与时序图
输入数据
pcap + log
→
特征提取
→
知识查询
GraphRAG
→
L1~L4 规则
→
LLM 诊断
→
报告

下文的重点是第 2 步：两种数据源分别提取出什么、如何进入后续判定，以及当前存在的具体问题。

2. 数据源说明

2.1 pcap 文件

pcap（Packet Capture）是保存网络报文的文件格式。本项目的仿真器（isis-simulator）用纯 Python 手工构造 IS-IS 报文写入 pcap 文件，每个场景文件包含 60~90 个报文，覆盖约 95 秒时间。

pcap 文件包含三层嵌套结构：

文件头
固定 24 字节
→
包记录头
每包 16 字节
→
以太网帧
每包 14+N 字节
→
IS-IS PDU
帧的载荷部分
  • 文件头：声明格式（魔数、版本、链路类型）
  • 包记录头：每条报文的时间戳与长度
  • 以太网帧：目的/源 MAC 地址、EtherType（IS-IS 固定为 0xFEFE）
  • IS-IS PDU：协议内容，包括报文类型、源 System ID、Holding Timer 等字段

2.2 log 文件

log 是设备打印的文本日志。本项目的仿真器按场景生成 2~3 行日志，例如 link-down 场景：

Jan 01 00:00:40 R02 IFNET: Interface Gig0/0/0 is Down
Jan 01 00:00:41 R02 ISIS: Adjacency to R01 (Gig0/0/0) is Down

解析器（log_parser.py）对每一行做正则匹配，识别出 10 类固定事件：

事件类型对应正则特征关联故障场景
adjacency_down / adjacency_upAdjacency ... is Down / is UP大多数故障
auth_failAuthentication failedauth-mismatch
area_mismatcharea mismatcharea-mismatch
circuit_type_mismatchCircuit type mismatchcircuit-type-mismatch
holding_timer_mismatchHolding timer mismatchhello-timer-mismatch
mtu_mismatchMTU mismatchmtu-mismatch
duplicate_system_idDuplicate System-IDduplicate-system-id
link_downInterface ... is Downlink-down
packet_lossPing ... packet lossnetem-loss-delay

注意：仿真 log 的内容是编写者预先固定写死的（log_generator.py），正则必然命中；真实网络中日志的内容和格式不固定，这一差别在后面分析问题时会再次提到。

3. pcap 字段级解析与特征提取

以下用 link-down 场景第 1 个包的真实数据（共 61 字节）逐层说明解析器（verify.py / pcap_feature.py）读到了什么。

3.1 文件头（24 字节）

d4 c3 b2 a1  02 00  04 00  00 00 00 00  00 00 00 00  00 00 04 00  01 00 00 00
└─魔数(小端)┘ └版本2.4┘ └────时区────┘ └时间精度┘ └链路类型=1(Ethernet)┘

解析器据此确认文件格式与字节序；链路类型=1 决定按以太网格式解析后续帧。

3.2 包记录头（每包 16 字节）

65 54 5f 40  00 00 00 00  3d 00 00 00  3d 00 00 00
└────秒────┘ └───微秒──┘ └本包帧长61┘ └原始长度61┘

时间戳（秒+微秒，共 8 字节）是 pcap 特征提取的关键输入，有两个用途：

  • 阶段归属：仿真器预先定义了三个时间窗口（scenario_lib.py）——before [0,30s)、fault [40,70s)、after [80,95s)（中间有 10s 间隙）。每个包按时间戳落入对应窗口。
  • 间隔计算：同一路由器相邻两个 Hello 包的时间差即为 Hello 发送间隔。

3.3 以太网帧头（14 字节）

01 80 c2 00 00 15 | 00 11 22 33 44 01 | fe fe
└──目的MAC(组播)──┘ └────源MAC────┘   └EtherType┘
  • 目的 MAC 01-80-c2-00-00-15 是 IS-IS 组播地址
  • 源 MAC 用于"重复 System ID"检测：同一个 System ID 若对应两个不同的源 MAC，说明存在两台设备抢同一 ID
  • EtherType 0xFEFE 表示载荷是 IS-IS（而非 IP 的 0x0800），决定后续解析分支

3.4 IS-IS PDU（载荷）

偏移: 0                               14                   22  23         28 29-30 31-32
      ├── 以太网头 14B ──┼─ IS-IS头 8B ─┼ 电路    SystemID 6B   Hold  PDU长度
      │                  │ 0x83+类型    │ 类型    (源路由器)   Timer (报文总长)
      01 80 c2 00 00 15 | 00 11 22 33 44 01 | fe fe | 83 1b 01 06 12 | 02 | 00 00 00 00 00 01 | 00 09 | 00 2f | ...
字段（帧内偏移）含义当前分析用途
固定标识 0x83（偏移14）IS-IS 报文标识确认是 IS-IS
PDU 类型（偏移18）0x12 = L2 Hello（保活）、0x15 = L2 LSP（路由泛洪）等区分保活流量与泛洪流量
电路类型（偏移22）1=L1、2=L2、3=两者电路类型不匹配检测
System ID（偏移23-28）发送方标识（R01=000000000001…）按源分桶统计
Holding Timer（偏移29-30，2字节大端）宣告的邻居保活超时（秒）参数不匹配检测
PDU 长度（偏移31-32）报文总长MTU 变化检测
TLV 区（偏移41起）可变字段：区域地址、主机名等区域地址用于区域不匹配检测

3.5 特征字典的形成（聚合过程）

解析器对文件内所有报文重复上述解析，然后做 分组统计：以（阶段窗口, 源 System ID）为分组键，每个分组内累加 Hello 包计数、收集源 ID / 区域 / Holding Timer 值集合、记录最大报文长度。最终形成一次分析使用的"特征字典"：

{
  "stages": {
    "before": {"iih_count": 28, "src_ids": [4台路由器], "holding_timers": [27],
               "areas": ["490001"], "pdu_types": ["L2_IIH"], "max_pdu_len": 47},
    "fault":  {"iih_count": 18, "src_ids": [R01,R03,R04],  ← R02 消失
               ...},
    "after":  {"iih_count": 14, "src_ids": [4台路由器], ...}
  },
  "icmp": {},
  "duplicate_system_id": false,
  "total_packets": 60
}
对 feature 步骤的结论：pcap 的解析与聚合是完整的，特征字典里已经包含了"R02 在故障窗口消失"这样直接指向故障的信号； log 的正则识别同样完整。分歧发生在"谁进入后面的判定"——见第 5 节。

4. 案例分析

4.1 link-down：如何从 60 个包得到"邻居丢失"信号

场景定义：R02 的物理链路在 fault 窗口断开，after 窗口恢复。

中间数据：按（阶段, 源ID）分组后，R02 的统计如下：

before/R02: 10 个 Hello 包，间隔 3 秒
fault/R02:  0 个包（该分组不存在）
after/R02:  5 个包，间隔 3 秒

判定规则（verify.py:219-222）：

if peer_before['iih_count'] > 0:              # 10 > 0，此前正常
    if peer_fault['iih_count'] == 0:          # fault 窗口 0 个包
        found.add("NEIGHBOR_LOSS_AT_FAULT")   # → 邻居丢失信号

两路数据对照：

数据源给出的内容
log"Interface Gig0/0/0 is Down"、"Adjacency ... is Down"（文本声明）
pcapR02 的 Hello 包 10 → 0 → 5（数值证据，含时间位置）

4.2 hello-timer-mismatch：如何从 90 个包得到"参数变更"信号

场景定义：R02 在 fault 窗口把 Hello 间隔从 3 秒改为 1 秒、Holding Timer 从 9 改为 10（hello_timer_mismatch.py）。

中间数据：

R02 同源时间戳序列:  before 最小间隔 3.0s | fault 最小间隔 1.0s
R02 Holding Timer 字段: before 0x0009=9s | fault 0x000a=10s  （帧偏移29-30）

判定规则（verify.py:237-251）：

if abs(1.0 - 3.0) > 0.2s  → HELLO_INTERVAL_CHANGE（Hello 周期变化）
if {9} != {10}             → HOLDING_TIMER_CHANGE（宣告参数变化）

两路数据对照：log 只给出文本"Holding timer mismatch"，而 pcap 给出了精确到参数值的证据（周期 3.0s→1.0s、Hold 9→10），并可定位到具体设备 R02。

5. 当前项目存在的问题

在给出优化方案之前，先梳理当前实现的具体问题。问题分为三组，均给出代码位置与影响。

5.1 问题组一：pcap 未参与诊断判定

编号问题代码位置实际影响
P1规则判定的唯一输入是 log 事件类型engine.py 的 _match_rule 仅将 log 提取的 event_types 与规则 indicators 做精确匹配L1~L4 每一层的 PASS/FAIL 完全由 log 决定；pcap 特征（如"R02 消失"）不影响任何规则
P2pcap 特征字典缺少 3 个关键字段pcap_feature.py 未保留 has_auth（认证标志）、按源时间戳序列（iih_ts）、LSP 时间明细；这些记账在 verify.py 中已实现但未传入特征字典即使要扩展 pcap 判定，认证故障、Hello 间隔变化、泛洪抑制三类场景没有可用数据
P313 类协议的异常检测逻辑与流水线断开verify.py 的 detect_anomalies（NEIGHBOR_LOSS_AT_FAULT 等）只在仿真器自检时使用；agent-analysis 仅复用其 read_pcap / decode_packet现成的 pcap 诊断能力（第 4 节已演示可检出 9/9 场景）完全未进入诊断报告
P4LLM 提示词中 pcap 摘要过于简化engine.py _build_llm_prompt 只写入 pdus 总数与 PDU 类型集合分阶段差异、源 ID 消失、定时器、区域、长度、ICMP 等细节丢失，LLM 无法使用这些证据

5.2 问题组二：GraphRAG 未参与最终结论

编号问题代码位置实际影响
P5GraphRAG 查询结果不进入 LLM 输入engine.py _build_llm_prompt 仅拼接特征摘要与命中规则，不含 knowledge_results知识图谱对最终结论贡献为零；报告中的"知识图谱结果"节只是展示性内容
P6知识查询词使用事件名原文engine.py _step_knowledge_query 将事件类型（如 "adjacency down"）直接作为查询词查询词与实体名字面一致，GraphRAG 退化为字面检索，图谱的实体映射与多跳关联能力未发挥
P7报告不标注知识来源，空结果视为命中engine.py 只判断 source 是否为 graphrag 即计数；graphrag_server server.py 对空响应仍返回 200 + source=graphragGraphRAG 降级到 CSV、或返回空回答时不可见，报告误导读者

5.3 问题组三：GraphRAG 服务可靠性缺口

编号问题代码位置实际影响
P8GraphRAG 回答依赖外部 LLM 配额LocalSearch 每次查询实时调用 chat 模型（kimi-k3）；配额耗尽时返回空 response（实测复现，journalctl 可见 usage limit 错误）有额度时正常，配额耗尽后所有查询返回空结果，且无错误提示
P9索引重建后服务未重启导致查询异常向量化器（output/tfidf_vectorizer.pkl）在服务启动时加载；重建索引会覆盖 pkl，运行中的服务仍使用旧向量化器查询向量维度/内容与索引不一致，检索返回空或异常（这是"LLM 正常但结果为空"的高频原因）
P10工作流自启实例与常驻服务端口冲突scripts_lib/runner.py start_graphrag_server 用系统 Python 再起 9200；端口被 systemd 服务占用时新实例启动失败，但 wait_for_service 探测到旧实例即判成功工作流的"就绪"检查是假阳性，若 systemd 服务不存在则该步直接失败降级
P11本地 TF-IDF 对中文查询无效local_embedding.py 使用词级 char_wb ngram；实测中文查询（如"邻居 断开"）产生全零向量，检索相似度全部为 0任何中文查询都无法检索到有效上下文
问题的整体关系：问题组一是"pcap 有用但没被用起来"，问题组二是"GraphRAG 建好了但与结论隔离"， 问题组三是"GraphRAG 即使想用也不稳定"。三个组的性质不同，对应第 6 节三个阶段的优化。

6. 优化方案（三个阶段）

每个阶段针对第 5 节的一组问题，给出改动文件与验收标准。阶段之间相互独立，可单独实施与回滚。

阶段 A：让 pcap 纳入规则判定（解决问题组一：P1~P4）

思路：把第 4 节已演示过的协议异常检测（verify.py 的 detect_anomalies）接入 agent-analysis，作为与 log 并列的第二条判定依据。

改动项文件内容
A1. 特征字典补充字段agent-analysis/src/agent_analysis/pcap_feature.py增加 has_auth（认证字段存在性）、按源时间戳序列（计算 Hello 间隔）、LSP 报文明细；可直接复用 verify.py 的分组记账逻辑
A2. 异常检测输出并入特征pcap_feature.py调用 detect_anomalies（或等价实现），把 13 类异常信号作为新特征字段 pcap_signals 输出
A3. 新增 pcap 驱动规则config/diagnosis_rules/*.json规则文件增加 pcap 信号映射，例如：NEIGHBOR_LOSS_AT_FAULT→L2 邻居丢失、HELLO/HOLDING_CHANGE→L2 参数变更、INTERFACE_MTU_CHANGE→L2 MTU 变化、LINK_PROBE_DEGRADATION→L4 丢包、CIRCUIT_TYPE_CHANGE→L2 电路类型
A4. 规则引擎支持 pcap 信号engine.py 的 _match_rule在现有 log 事件匹配之外，增加 pcap 信号匹配分支；两条路径并存，各自独立命中
A5. 报告增加"pcap 协议信号"节engine.py 的 _build_report展示每条信号的数值证据（如 R02 IIH 10→0、Hello 间隔 3.0s→1.0s），与 log 命中并列
验收标准：用 9 个场景的 pcap 运行分析，规则命中应同时来自两路——例如 link-down 同时命中 "log: adjacency_down" 与 "pcap: NEIGHBOR_LOSS_AT_FAULT"；baseline 场景两路均不命中；已有测试（tests/）不回归。

阶段 B：让 GraphRAG 知识进入 LLM 诊断（解决问题组二：P5~P7）

思路：把知识查询结果真正作为 LLM 的诊断依据，同时改善查询质量与可追溯性。

改动项文件内容
B1. LLM 提示词注入知识结果engine.py 的 _build_llm_prompt在命中规则之后追加"知识图谱参考"节（节点描述、关联根因、参考文档），要求 LLM 引用其中的依据
B2. 查询词改造engine.py 的 _step_knowledge_query将事件名组合成开放问题（如"link_down 与 adjacency_down 同时出现的原因、影响与排查步骤"），触发图谱的实体映射与跨节点检索
B3. pcap 信号并入查询来源engine.py把 pcap_signals 一并生成知识查询，使协议层信号（如 NEIGHBOR_LOSS_AT_FAULT）也能获得知识支撑
B4. 报告标注知识来源engine.py 的 _build_report；graphrag/src/graphrag_server/server.py每条知识结果标注来源（graphrag / csv_fallback / 本地 CSV）；服务端对空回答不标注为 graphrag 命中
验收标准：同一输入分别以 GRAPHRAG_ENABLED=false 与 true 运行，比较 LLM 结论——开启时应多出可溯源到"知识图谱结果"节的额外依据（根因排序、参考文档引用）。

阶段 C：GraphRAG 服务可靠性治理（解决问题组三：P8~P11）

思路：先让 GraphRAG 在可用的前提下保持稳定，否则阶段 B 的效果无法保证。

改动项文件 / 操作内容
C1. 空回答按失败处理graphrag/src/graphrag_server/server.pyLocalSearch 返回空 response 时改为降级 CSV 并标记 source=csv_fallback，不再以"空 graphrag 命中"返回
C2. /health 返回完整状态server.py增加索引构建时间、向量化器版本、最近一次查询是否异常等字段，供运维判断服务是否可用
C3. 索引重建后自动重启服务knowledge-builder 工作流（skills/knowledge-builder/run.py）build graphrag-index 完成后若服务在运行，则自动重启（systemctl --user restart isis-graphrag.service），保证向量化器与索引一致
C4. 自启实例复用已有服务scripts_lib/runner.py 的 start_graphrag_server启动前先探测 9200 是否存在健康实例，存在则直接复用并返回哨兵对象，避免端口冲突与假健康
C5. 中文查询映射local_embedding.py 或查询侧对中文查询词先做词典映射到英文实体名，或扩充 TF-IDF 语料覆盖中文表达
C6. 模型可用性监控运维侧跟踪 kimi 配额使用情况（当前已耗尽），或在有条件时按 docs/MODEL_CONFIGURATION.md 迁移内网 vLLM 端点
验收标准：服务可用时 /query 返回非空 graphrag 结果；配额或索引异常时 /query 明确返回 csv_fallback 或错误，报告与 /health 状态一致。

优化后的判定逻辑：log 与 pcap 命中一致时结论置信度最高；两者矛盾时（例如 log 正常但 pcap 检出邻居丢失）， 由 LLM 依据两路证据与知识图谱给出"疑似静默故障"的判断，并在报告中明确列出两路证据与知识来源。
